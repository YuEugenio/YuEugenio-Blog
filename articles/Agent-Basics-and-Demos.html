Agent Basics and Demos

This article places tool use, observation loops, streamed interaction, and ReAct-style execution inside one agent perspective, and explains why an agent is fundamentally a structured execution system rather than a better prompt.

March 13, 2026

Technical Explainer

The key difference of an agent is not stronger personality. It is clearer execution structure. Once a task is split into thought, action, observation, and final response, the model begins to act like a system that can work step by step rather than a one-shot generator.

Primary Material
`draft.py` and `travelassistant.py`, covering streamed interaction and tool-use loops.
Learning Object
The shift from a single completion call to an explicit tool-using execution loop.
Current Output
A minimal ReAct-style agent is already working, and control logic is clearly more important than prompt size alone.

1. Theme

The object of this article is not the label “agent” by itself. It is the point at which a model stops only answering and starts executing a task. As soon as a system must decide whether to call a tool, how to read an observation, whether to continue iterating, and when to stop, it is no longer a plain completion call. It is a minimal execution framework.

The learning focus is therefore not on style or personality. It is on making steps explicit. Once the execution loop is written clearly, the system becomes easier to debug, easier to extend, and easier to diagnose when failure comes from planning, tool use, or result integration.

2. Principle

The central principle of an agent is stateful execution. The model does not only read input and answer. It first decides whether an external action is needed, then writes tool output back as a new observation, and only then continues the decision process. Capability therefore comes not only from model parameters, but also from action format, tool interfaces, and loop control.

ReAct is especially useful as an entry framework because Thought, Action, and Observation are explicitly separated. Even in a simplified implementation, that structure already shows the essential difference between an agent and a plain chat call.

Explicit Actions

Once tool calls are separated from answer text, system behavior is no longer controlled only by the final response.

Observation Writeback

Tool results become inputs to the next decision step, which is what gives the loop iterative power.

Control Logic

Action parsing, format constraints, and stop rules often matter more than one large prompt.

3. Practice and Implementation

`draft.py` focuses on streamed output and the separation between reasoning-style display and the visible answer. `travelassistant.py` connects tool calls, weather lookup, and attraction search inside a simplified ReAct loop so Thought, Action, and Observation can occur in sequence.

These two scripts expose two major sides of agent behavior. The first is interaction-layer design, where internal progress and visible output may not be the same thing. The second is task-layer design, where the model takes on coordination responsibility because tools and observations have been built into the loop.

Failure Diagnosis

4. Current Output

This study already supports one clear judgment: agent capability mainly comes from process design rather than from abstract “smartness.” Once actions, tools, observations, and finish conditions are organized clearly, even a very small demo can show the difference between task execution and one-turn answering.

That also means future progress will not mainly come from writing a larger prompt. It will come from designing cleaner execution structure as retrieval, state graphs, memory, and external system integration are added.

5. Conclusion

An agent is not a model shell that chats better. It is a system that organizes reasoning, action, observation, and answering into an execution loop. Once that perspective is established, later topics such as tool orchestration, workflow graphs, and multi-step task design become much easier to interpret.
