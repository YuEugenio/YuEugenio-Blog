GreenForest_RAG: A Project Brief

This article defines the GreenForest_RAG task object, explains the retrieval-augmented pipeline, summarizes the current demo scope, and states the engineering conclusion already supported by this small domain knowledge base.

March 13, 2026

Project Article

GreenForest_RAG reorganizes gardening and project-operation materials into a searchable local knowledge base. The current objective is not interface richness, but a complete path from document ingestion to evidence-grounded answering.

Knowledge Sources
Mixed PDF, DOCX, and CSV materials covering plant care, planning, operations, records, and data tables.
Core Goal
Turn scattered files into a traceable retrieval system instead of depending on unconstrained generation.
Current Interface
A local CLI retrieval-and-answer demo built on LangChain and Chroma.

1. Theme

GreenForest_RAG is a domain-oriented RAG prototype. Its source materials are not open-web pages, but the local document archive around the “萃意生机” balcony-ecology project. Those materials mix horticultural knowledge with business and operational information, which makes the setup much closer to a real project knowledge environment.

The object of this article is therefore not one model parameter choice. It is the conversion of a document pile into a system that can retrieve, cite, and answer from project knowledge in a disciplined way.

2. Principle

The logic is simple but precise. RAG does not mainly make a model “more eloquent.” It makes the answer depend on retrievable evidence. In a project environment where knowledge is fragmented across heterogeneous files, that organization is more reliable than direct chatting and more efficient than manual file-by-file lookup.

GreenForest_RAG therefore follows a four-step method. First, read mixed local files into a unified document interface. Second, split long text into retrieval-friendly semantic segments. Third, embed those segments and persist them in a local vector store. Fourth, answer only after retrieval, with the model constrained to the returned evidence.

Method Boundary

The current demo answers the question of reliable knowledge recall. It does not yet solve product-layer concerns such as access control, web UI, scheduled ingestion, or production monitoring.

3. Implementation

The current build uses LangChain UnstructuredLoader for local PDF, DOCX, and CSV materials, RecursiveCharacterTextSplitter for chunking, and an OpenAI-compatible embedding configuration for vectorization. Model and interface parameters have already been moved into environment variables so the scripts are less tightly coupled to one fixed runtime.

Chroma is used as the persistent vector store. Running `RAG.py` performs document scanning, loading, splitting, embedding, and persistence. Running `ask.py` then starts the command-line answer loop on top of the existing index.

The most important constraint at answer time is retrieval first, response second. The retriever selects the most relevant passages and metadata, packages them into context, and then sends the question plus evidence to the model. If the indexed material is insufficient, the prompt prefers an explicit “do not know” answer over unsupported completion.

Ingestion Layer

The first job is to normalize mixed-format files into one processing interface.

Index Layer

Chunking, embeddings, and Chroma persistence together form the minimal knowledge substrate.

Answer Layer

The question passes through retrieval before generation, which keeps answers tied to explicit context.

4. Demo Results

The current demo already completes the path from local documents to grounded answers. It turns content scattered across manuals, planning files, spreadsheets, and meeting notes into retrievable project knowledge, and it can return relevant passages quickly when a user asks a question.

For this project, the main observation is not whether the answer sounds polished. The main observation is whether the answer can be traced back to indexed material. Once that condition is satisfied, chunk strategy, metadata design, retrieval parameters, and answer prompts all become concrete and improvable objects.

Retrieval First

The system looks for evidence before it speaks, so answer quality is directly coupled to index quality.

Local Persistence

Chroma avoids rebuilding the knowledge base from scratch for every new question.

Optimization Targets

Document quality, chunking, metadata, and top-k retrieval are now explicit variables instead of vague intuition.

5. Conclusion

GreenForest_RAG already demonstrates that a small domain knowledge base can be turned into a stable knowledge-recall system through RAG. The most important outcome is not interface completeness, but the fact that evidence-grounded answering is already working at the engineering level.

That gives later work a reliable base to build on. The project no longer needs to fall back to a folder of scattered files and human memory as the main retrieval mechanism. The reorganization of knowledge is itself the product value.
